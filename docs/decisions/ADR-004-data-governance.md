# ADR-004: 데이터 거버넌스 기준

- 문서 상태: `approved`
- 결정일: 2026-07-23
- 구현 상태: [검증 필요] 미구현
- 관련 문서: [데이터 전략](../data/data-strategy.md), [데이터 전처리](../data/preprocessing.md), [데이터셋 레지스트리](../data/dataset-registry.md), [데이터 라이선스 정책](../data/data-license-policy.md), [데이터 분할 및 누수 방지](../data/data-split-and-leakage-policy.md)

## 결정 배경

DohaLM은 토크나이저부터 `DohaLM-Tiny` 사전학습과 SFT까지 직접 수행한다. 모델 구현이 정확해도 데이터 출처·권리·변환·분할이 추적되지 않으면 학습을 재현하거나 결과 공개 가능성을 판단할 수 없다. 현재 실제 데이터가 없으므로 취득과 구현 전에 공통 거버넌스 기준을 결정한다.

- [확정] 데이터셋 선택과 전처리는 모델 품질뿐 아니라 라이선스, 개인정보, 누수와 공개 가능성에 영향을 준다.
- [확정] 실제 후보·규모·필터 임계치는 아직 결정하지 않는다.

## 구현보다 먼저 정하는 이유

- [확정] 승인되지 않은 데이터를 먼저 취득·처리해 발생하는 삭제·재작업을 줄인다.
- [확정] 전처리 코드가 원본을 덮어쓰거나 계보를 잃는 구조로 굳어지는 것을 방지한다.
- [확정] 토크나이저·사전학습·SFT·평가 데이터의 목적과 누수 경계를 구현 계약으로 제공한다.
- [확정] checkpoint와 모델 카드에 필요한 dataset·split 식별자를 처음부터 포함할 수 있다.

## 고려한 대안

| 대안 | 장점 | 위험 | 결정 |
|---|---|---|---|
| 데이터 확보 후 기록 | 시작이 빠름 | 출처·조건·변환 계보 유실 | [제외] |
| 파일명과 로컬 메모만 관리 | 단순함 | 재현·감사·삭제 영향 추적 불가 | [제외] |
| registry·checksum·manifest 기반 관리 | 승인과 계보를 구조화 | 초기 문서·운영 비용 | [확정] 채택 |

## 결정 사항

### 원본 불변 원칙

- [확정] 취득한 원본은 직접 수정하거나 덮어쓰지 않는다.
- [확정] 정제·분할·토큰화 결과는 별도 version으로 생성한다.
- [확정] 원본 checksum과 모든 파생 version을 연결한다.

### 데이터셋 레지스트리 채택

- [확정] 모든 실제 후보는 취득 전에 registry에 `candidate`로 등록한다.
- [확정] 상태는 `candidate`, `reviewing`, `approved`, `rejected`, `downloaded`, `processed`, `deprecated`를 사용한다.
- [확정] 승인은 특정 dataset version과 사용 목적에 부여한다.

### 라이선스 불명확 데이터 제외

- [확정] 출처·제공자·이용조건을 확인할 수 없으면 `approved`로 전환하지 않는다.
- [확정] 학습, 수정, 재배포, 파생 모델 공개와 attribution 조건을 별도로 기록한다.
- [법률 검토 필요] 조건 해석이 불명확하면 임의로 허용 결론을 내리지 않는다.

### 전처리 버전 관리

- [확정] normalization, 필터, dedup, 문서 경계, split과 packing 설정을 전처리 version에 연결한다.
- [확정] 규칙 변경은 기존 결과를 덮어쓰지 않고 새 version을 만든다.

### Checksum과 manifest 관리

- [확정] 원본과 주요 파생 산출물에 checksum 또는 동등한 무결성 식별자를 둔다.
- [확정] manifest에는 입력·출력, version, 설정, 코드 revision, 통계, 제외 사유와 계보를 기록한다.
- [검증 필요] hash 알고리즘, manifest schema와 저장 위치는 구현 전에 확정한다.

### Train/validation/test 누수 방지

- [확정] exact·near duplicate를 고려해 문서·출처·문제 그룹 단위로 분할한다.
- [확정] split 후 fingerprint 교차 검사를 수행하고 seed·split version을 기록한다.
- [확정] SFT 답변, 고정 prompt와 외부 benchmark 오염을 일반 중복과 별도로 검사한다.
- [제외] 리더보드 비공개 평가 데이터를 복원·추정하려는 시도를 금지한다.

## 장점

- [확정] 데이터 사용 근거와 변환 계보를 재현할 수 있다.
- [확정] 라이선스 변경·삭제 요청·오염 발견 시 영향 산출물과 실험을 추적할 수 있다.
- [확정] 토크나이저, checkpoint, 평가와 모델 카드의 호환성 정보를 일관되게 연결한다.
- [확정] 후보·승인·취득·처리 상태를 구분해 미검토 데이터를 사용하지 않게 한다.

## 단점

- [확정] 초기 등록·검토·manifest 생성 비용이 증가한다.
- [확정] 개인정보·유해성·근사 중복 검사는 자동화만으로 완결되지 않아 사람 검토가 필요할 수 있다.
- [확정] 엄격한 출처·라이선스 기준으로 사용 가능한 데이터 규모가 줄 수 있다.
- [검증 필요] 제한된 개인 프로젝트 환경에서 운영 가능한 자동화와 검토 깊이를 조정해야 한다.

## 구현 영향

- [확정] 데이터 파이프라인은 원본 read-only, versioned output과 manifest 생성을 지원해야 한다.
- [확정] dataset loader와 학습 checkpoint는 dataset ID, preprocessing version, split version과 tokenizer ID를 기록해야 한다.
- [확정] exact·near duplicate, split 교차 검사와 품질 검사 결과를 테스트할 수 있어야 한다.
- [확정] 실제 데이터 본체와 민감 로그는 Git에서 제외하고 소형 registry·schema·통계만 추적 후보로 둔다.
- [검증 필요] registry·manifest 저장 형식과 validation 도구는 후속 구현에서 결정한다.

## 재검토 조건

- [검증 필요] 실제 데이터 제공 조건이 현재 상태·필드로 표현되지 않는다.
- [검증 필요] registry·manifest 운영 비용이 파이프라인 검증을 지속적으로 막는다.
- [검증 필요] 삭제 요청·라이선스 변경·누수 사고에서 계보 추적이 충분하지 않다.
- [검증 필요] 외부 제출·모델 공개 조건이 더 엄격한 데이터 기록을 요구한다.
- [확정] 원본 변경, 라이선스 불명확 데이터 허용 또는 누수 기준 완화는 후속 ADR 없이 적용하지 않는다.
