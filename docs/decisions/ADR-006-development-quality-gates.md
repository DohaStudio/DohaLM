# ADR-006: 개발 단계와 품질 게이트

- 상태: `approved`
- 결정일: 2026-07-23
- 구현 상태: `[검증 필요]` 미구현
- 관련 문서: [개발 로드맵](../quality/development-roadmap.md), [테스트 체크리스트](../quality/testing-checklist.md), [Definition of Ready](../governance/definition-of-ready.md), [Definition of Done](../governance/definition-of-done.md), [테스트 전략](../quality/test-strategy.md), [위험 등록부](../governance/risk-register.md), [Codex 작업 절차](../governance/codex-workflow.md)

## 1. 결정 배경

- [확정] DohaLM은 데이터, 토크나이저, 모델, 학습, 평가, SFT, 서비스가 순차적으로 의존하는 프로젝트다.
- [확정] `RTX 3060 Ti 8GB` 단일 GPU에서는 뒤늦게 발견한 shape 오류, OOM, 데이터 문제로 인한 재실행 비용이 크다.
- [확정] 문서 작성, 코드 존재, 학습 시작을 각각 구현 완료로 오인하지 않도록 단계별 진입·통과 기준이 필요하다.
- [확정] 장시간 학습이나 서비스 구현에 앞서 작은 입력과 짧은 실행으로 실패를 조기에 확인해야 한다.

## 2. 고려한 대안

### 대안 A: 기능을 모두 구현한 뒤 일괄 검증

- [제외] 초기 진행은 빠르게 보일 수 있으나 실패 원인과 회귀 범위가 커진다.

### 대안 B: 일정만으로 다음 단계 진입

- [제외] 산출물과 테스트 상태를 보장하지 못하며 GPU 비용과 데이터 위험을 통제하기 어렵다.

### 대안 C: 단계별 Ready·Done·품질 게이트 적용

- [확정] 각 단계의 선행 조건, 필수 산출물, 테스트, 실패 시 복구 경로를 명시한다.

## 3. 결정

- [확정] [개발 로드맵](../quality/development-roadmap.md)의 Phase 0~10과 Gate 0~11을 공식 개발 순서와 품질 관문으로 채택한다.
- [확정] 작업 착수 전에는 [Definition of Ready](../governance/definition-of-ready.md)를, 완료 선언 전에는 [Definition of Done](../governance/definition-of-done.md)을 적용한다.
- [확정] 필수 테스트가 실패하거나 실행되지 않은 작업은 완료 처리하지 않는다. 미실행은 사유와 차단 영향을 기록한다.
- [확정] 문서와 ADR을 구현보다 먼저 동기화하며, 문서 상태 `approved`와 구현 상태 `implemented`를 구분한다.
- [확정] 작은 단위 테스트, 통합 smoke, Tiny overfit을 통과한 뒤에만 장시간 DohaLM-Tiny 사전학습을 제안한다.
- [확정] 장시간 학습, 서비스 단계 진입, 배포와 외부 제출은 해당 게이트 외에 사용자의 명시적 승인을 요구한다.
- [확정] Codex 작업에는 [Codex 작업 절차](../governance/codex-workflow.md)의 범위 확인, 검증, 완료 보고, Git 안전 규칙을 적용한다.

## 4. 실패와 롤백 원칙

- [확정] 게이트 실패 시 다음 단계로 진행하지 않고 마지막으로 통과한 게이트의 산출물을 기준점으로 삼는다.
- [확정] 실패 원인, 재현 입력, 환경, 로그, 영향 범위와 대응 결과를 실험 기록 또는 작업 보고에 남긴다.
- [확정] OOM은 [GPU 메모리 전략](../training/gpu-memory-strategy.md)의 조정 순서를 적용하고, 데이터·평가 문제는 해당 거버넌스 문서로 되돌아간다.
- [확정] 변경을 되돌릴 때 사용자 작업을 덮어쓰거나 Git 이력을 강제로 재작성하지 않는다.

## 5. 장점

- [확정] 실패를 작은 범위에서 발견해 GPU 시간과 디버깅 비용을 줄인다.
- [확정] 완료 주장에 필요한 근거가 문서, 테스트, 산출물로 분리된다.
- [확정] 재현성과 체크포인트·데이터 계보가 단계마다 확인된다.
- [확정] Codex와 사용자의 승인 경계가 명확해진다.

## 6. 단점

- [확정] 각 단계에 문서와 증거를 준비해야 하므로 초기 진행 속도가 느려질 수 있다.
- [확정] 아직 정량 임계값이 없는 게이트는 사람의 검토와 추가 결정을 요구한다.
- [확정] 작은 프로젝트 단계에서도 상태 관리 비용이 발생한다.

## 7. 구현에 미치는 영향

- [확정] 테스트 가능한 작은 구성요소와 명시적 입력·출력 계약을 우선해야 한다.
- [확정] 학습 루프는 smoke, overfit, checkpoint resume, NaN/Inf와 OOM 대응을 검증할 수 있어야 한다.
- [확정] 실험 산출물은 설정, Git SHA, seed, 데이터·토크나이저 fingerprint와 평가 결과를 연결해야 한다.
- [검증 필요] 실제 테스트 명령, CI 분할, 정량 합격 임계값은 구현 전에 확정한다.
- [검증 필요] 이 ADR 승인만으로 코드, 테스트, 학습 또는 릴리스가 구현된 것은 아니다.

## 8. 재검토 조건

- [검증 필요] 단계 순서가 실제 의존 관계와 맞지 않아 반복적으로 우회가 필요한 경우
- [검증 필요] 하드웨어나 학습 방식 변경으로 현재 게이트가 비용·위험을 통제하지 못하는 경우
- [검증 필요] 자동화된 테스트와 CI가 도입되어 승인 책임과 게이트 증거가 달라지는 경우
- [검증 필요] DohaLM-Small 또는 외부 배포가 주 범위가 되어 별도 품질 체계가 필요한 경우
- [검증 필요] 테스트 실패가 없는데도 게이트가 과도하게 진행을 차단하거나, 반대로 결함을 놓치는 경우
